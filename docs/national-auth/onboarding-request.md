# בקשת חיבור למערכת ההזדהות הלאומית — טיוטה להגשה למערך הדיגיטל

טיוטה למילוי והגשה מול מערך הדיגיטל (SAML 2.0, נספח טכני v2.4). שדות המסומנים
**[למילוי]** תלויים בהחלטת ה-Gateway ובפרטי הרשות/התעודות ואינם ניתנים לקביעה מצדנו.

## 1. פרטי הגורם המבקש
- שם הרשות / הגוף: **[למילוי]**
- מספר רשות (אם רלוונטי): **[למילוי]**
- שם היישום/השירות: מערכת טפסים דיגיטליים לתושב (Salesforce Experience) — הדגמה: "עיריית מוניפורס"
- איש קשר טכני (שם/טלפון/דוא"ל): **[למילוי]**
- איש קשר מנהלי: **[למילוי]**

## 2. סביבה מבוקשת
- **סביבת בדיקות** — `https://st.login.gov.il` (נתחיל כאן).
- עלייה לייצור בהמשך, לאחר בדיקות PT ואישור חיבור.

## 3. ארכיטקטורת החיבור (חשוב — מגדיר את שאר הבקשה)
- ה-SP הוא **מוצר SAML מדף (Gateway)** — **לא** Salesforce. אין פיתוח SP עצמי.
- היישום עצמו (הטופס) הוא **אנונימי (Guest)**; **אין הקמת משתמשי תושב ואין רישוי תושבים**.
- לאחר הזדהות מוצלחת ב-Gateway, הזהות המאומתת (ת״ז + שם) מועברת ליישום ב**טוקן חתום קצר-מועד**
  (הזדהות **אחת בלבד**, ללא כפל הזדהות).
- סוג ה-Gateway: **[למילוי — בחירה]**
  - ☐ שירות המתארח במערך הדיגיטל (מערך הדיגיטל משמש כ-SP ומנתב חזרה לכתובת לא-מזוהה)
  - ☐ ברוקר/שער זהויות קיים של הרשות (מוצר SAML מאושר)
  - ☐ הקמת SP מדף ייעודי (למשל Keycloak/SimpleSAMLphp/Shibboleth) כ-Gateway

## 4. נתוני ה-SP (Gateway) לרישום ויצירת Trust
- `entityID` של ה-SP: **[למילוי]** (רצוי שיכיל את כתובת היישום)
- `AssertionConsumerService` (ACS), עדיפות **HTTP-POST**: **[למילוי]**
- `SingleLogoutService` (SLO), Location + ResponseLocation: **[למילוי]**
- `NameIDFormat`: `urn:oasis:names:tc:SAML:2.0:nameid-format:unspecified` (הערך = מספר הזהות)
- תגית `validUntil`: לא לכלול.
- קובץ **Metadata** של ה-SP: יצורף בנפרד (ראה `sp-metadata.template.xml`).

## 5. תעודות והצפנה (בצד ה-Gateway)
- חתימה: **RSA-SHA256** · הצפנה: **AES256**.
- תעודה: **[למילוי]** — self-signed מותר **בבדיקות בלבד**; לייצור נדרשת תעודת CA מוכר או תמו״ז.
- ה-AuthnRequest וה-LogoutRequest ייחתמו במפתח הפרטי של ה-SP.

## 6. פתיחת תקשורת (סביבת הבדיקות סגורה)
- כתובות ה-**IP הציבוריות** של ה-Gateway (ושל תחנות הבדיקה) לפתיחה מול `st.login.gov.il`: **[למילוי]**

## 7. מאפיינים מבוקשים (Attributes)
| שדה | נדרש | הערה |
|---|---|---|
| `IDNum` | כן | מספר זהות (9 ספרות) = ה-NameID |
| `HebName` | כן | שם פרטי (עברית) |
| `HebLastName` | כן | שם משפחה (עברית) |
| `LOA` | כן | רמת הבטחת אימות (רב״א); מינימום מבוקש: **3** |
| `Mail` | לא | אם קיים |
| `Mobile` | לא | אם קיים |
| `PreferredLang` | לא | שפה מועדפת |

## 8. מנגנון ניתוק
- ניתוק דרך `https://st.gov.il/mw/logout.html?forwardURL=<כתובת לא-מזוהה>` (בדיקות),
  ובייצור `https://gov.il/mw/logout.html?...`. הכתובת שאליה מנתבים לאחר ניתוק אינה מזוהה.

## 9. הערות
- מודל "זיהוי לטופס בלבד": אין ניהול Session מתמשך ביישום; הטוקן קצר-מועד וחד-פעמי (nonce).
- נבקש לתאם את **חוזה הטוקן** (מפתח ציבורי/סוד משותף, claims: IDNum/HebName/HebLastName/LOA/nonce,
  TTL, audience) מול הגורם המפעיל את ה-Gateway.

## מה נדרש להמשך (סדר פעולות)

**אצל הרשות / מולכם:**
1. להחליט על ה-Gateway (סעיף 3) — זו ההחלטה החוסמת; היא קובעת entityID/ACS/תעודה/טוקן.
2. להגיש את בקשת החיבור הזו למערך הדיגיטל ולקבל איש קשר לאינטגרציה.
3. לבקש פתיחת IP לסביבת הבדיקות (IP של ה-Gateway).
4. להנפיק/להשיג תעודת SP (self-signed לבדיקות).
5. להחליף Metadata (SP↔IdP) ולתאם את חוזה הטוקן.

**אצלי (אחרי בחירת ה-Gateway):**
6. לבנות בצד Salesforce את מאמת-הטוקן (`NationalIdentityController.verifyToken`) ואחסון המפתח/סוד באופן מוגן.
7. לחווט ב-dynamicForm: שער כניסה + מילוי-מוקדם ונעילה של ת״ז/שם לפי `Identity_Mode`.
8. כפתור "כניסה עם הזדהות לאומית" מעוצב + קישור ניתוק.
9. בדיקות קצה-לקצה מול סביבת הבדיקות.
